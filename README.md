# Explainable AI Fraud Detection

A full-stack fraud detection system that doesn't just flag a transaction -
it explains which features drove the decision, using SHAP. Three
architecture pieces: `ai-model/` (training notebooks + serialized
models), `backend/` (a Dockerized FastAPI inference service), and
`frontend/` (a Next.js dashboard).

## The model

Trained on the standard Kaggle credit card fraud dataset (`creditcard.csv`):
284,807 transactions, 492 fraudulent (**0.173%** - a genuinely severe
class imbalance, handled with a stratified train/test split rather than
resampling). Features are `Time`, `Amount`, and `V1`-`V28` (already
PCA-anonymized in the source dataset).

Three models were trained and compared (`ai-model/2_Model_Training.ipynb`),
evaluated on fraud-class precision/recall since accuracy alone is
meaningless at this class imbalance:

| Model | Precision (fraud) | Recall (fraud) | F1 (fraud) |
|---|---|---|---|
| Logistic Regression (baseline) | 0.83 | 0.64 | 0.72 |
| **Random Forest** | **0.94** | **0.82** | **0.87** |
| Neural Network (MLP, 1 hidden layer of 100) | 0.92 | 0.81 | 0.86 |

Random Forest and the MLP are both shipped to production; Logistic
Regression was a baseline only. `Time` and `Amount` are scaled with
`StandardScaler` instances fit during training and serialized
(`amount_scaler.joblib`, `time_scaler.joblib`) so the API applies the
*exact* same transform at inference time - the classic training/serving
skew bug that causes silently wrong production predictions.

## Backend (`backend/app/`)

- **`POST /predict`** - runs Random Forest *and* the neural network on the
  same input and returns both models' individual predictions and
  probabilities. The final verdict is an OR: if *either* model flags a
  transaction as fraud, the response is `"Fraud"`. This is closer to a
  two-model ensemble catching what either one might miss than a
  primary/challenger setup.
- **`POST /explain`** - runs SHAP's `TreeExplainer` (built against the
  Random Forest specifically, using a 100-sample background dataset
  captured at training time) and returns the top 5 features by absolute
  impact on the fraud score, plus the explainer's base value - this is
  what powers the force-plot-style breakdown in the UI.
- Both endpoints take strictly-typed Pydantic input (`Time`, `Amount`,
  `V1`-`V28` as required floats) - malformed payloads get rejected by
  FastAPI's validation before reaching either model.
- Models, scalers, and the SHAP explainer are all loaded once at startup
  (FastAPI `lifespan`) into an in-memory cache, not reloaded per request.
- `backend/Dockerfile` containerizes the service for deployment.

## Frontend (`frontend/`)

Next.js (TypeScript, Tailwind) dashboard - submits a transaction to
`/predict`, then calls `/explain` to render the SHAP feature breakdown
for the flagged transaction.

## Running locally

```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
# needs backend/saved_model/*.joblib and background_data.csv present -
# generated by running ai-model/2_Model_Training.ipynb end to end

cd ../frontend
npm install
npm run dev
```

## Current state

The `/predict` OR-ensemble logic means the system is tuned toward higher
recall (catching more fraud) at the cost of more false positives, since
either model alone can trigger a fraud verdict - worth knowing before
citing a single model's precision/recall table as *the* system's
real-world behavior. There's no CI workflow in this repo despite the
Docker setup being deployment-ready; that would be the natural next
addition before treating this as fully production-hardened.
